# Микросервисная архитектура — карта сервисов и путь выделения

Документ фиксирует, как модульный монолит `app/` устроен под будущую декомпозицию
на сервисы. Функциональные требования — в [SPEC.md](SPEC.md); здесь — только
архитектурные границы, контракты и порядок выделения.

## 1. Текущая фаза: модульный монолит с bounded contexts

`app/` разделён на изолированные доменные модули. Каждый домен — потенциальный
самостоятельный сервис: у него собственные `api.py` (HTTP-слой), `schemas.py`
(контракты), `services.py` (бизнес-логика) и `models.py` (данные).

```text
app/
  main.py                  # composition root: собирает роутеры всех доменов
  core/                    # shared kernel — то, что общее для всех сервисов
    config.py              #   Settings из env
    db.py                  #   engine + session factory
    deps.py                #   FastAPI-зависимости (get_db → будущий auth-контекст)
    base.py                #   DeclarativeBase, JSONType, naming convention
  platform/                # platform domain: /api/health и метаданные
  domains/
    identity/              # пользователи, роли, сессии, auth
    cases/                 # дела проверок, статусы, события
    documents/             # загрузка файлов, извлечение, факты
    analysis/              # правила, запуски, сигналы, решения
    reporting/             # сборка отчёта (без собственных таблиц)
```

Правила изоляции (соблюдаются уже сейчас):

- Домены **не импортируют** `api.py`/`services.py` друг друга. Общие типы —
  только модели через `TYPE_CHECKING`-ссылки и enum'ы.
- HTTP-слой (`api.py`) не содержит бизнес-логики — только валидация схем и вызов
  `services.py`.
- `services.py` не знает о FastAPI — принимает ORM-сессию, возвращает данные.
  Это позволяет позже вынести сервис в отдельный процесс без переписывания.

## 2. Карта сервисов

| Сервис | Ответственность | Владеет таблицами | Публичный API (SPEC §4) |
|---|---|---|---|
| `platform` | health, версия, метаданные | — | `GET /api/health` |
| `identity` | регистрация/вход, роли, сессии, `me` | `users`, `sessions` | `/api/auth/*` |
| `cases` | CRUD дел, `stale`/`pending_count`, audit-лента | `cases`, `case_events` | `/api/cases*`, `/api/events` |
| `documents` | приём файлов, pipeline, факты | `documents`, `facts` | `/api/cases/{id}/documents`, `/api/facts*` |
| `analysis` | правила, запуски, сигналы, решения | `analysis_runs`, `signals`, `signal_facts`, `decisions` | `/api/rules`, `/api/analysis*`, `/api/signals*`, `/api/decisions` |
| `reporting` | агрегация отчёта по делу | — (читает чужие данные) | `/api/cases/{id}/report` |

### Границы данных (data ownership)

- Каждый сервис **владеет** своими таблицами: только его код пишет в них.
- `reporting` — единственный read-only потребитель чужих таблиц; при выделении
  в сервис перейдёт на синхронные вызовы/события (см. §5).
- Связи `Case → documents/facts/runs` — **швы выделения**: в монолите это ORM-
  relationship, в микросервисах — API-вызовы или реплицируемые read-модель.

## 3. Shared kernel (`app/core/`)

То, что остаётся общим даже после разделения на процессы:

- **config** — `Settings` из переменных окружения (у каждого сервиса свой экземпляр).
- **db** — подключение к БД; при database-per-service у каждого сервиса свой
  `database_url` и своя схема.
- **deps** — точка внедрения auth-контекста. Сейчас `get_db`; после выделения
  `identity` сюда добавится `get_current_user` (internal token / forwarded claims).
- **base** — ORM-базовый класс и переносимые типы колонок.

Сознательно **не** в shared kernel: доменные enum'ы, схемы, сервисы — они живут
внутри своих bounded contexts.

## 4. Версионирование и контракты

- Текущий публичный префикс `/api` соответствует **v1**. Клиент уже завязан на
  него (vite-proxy, nginx), поэтому разрыв контракта недопустим.
- При появлении lомающих изменений вводится `/api/v2/...`; v1 живёт до миграции
  клиента. Внутри каждого домена схемы `schemas.py` версионируются вместе с API.
- OpenAPI (`/openapi.json`) — единая точка правды о контрактах; e2e-тесты клиента
  проверяют его на соответствие `flow.spec.ts`.

## 5. Синхронные и асинхронные контракты

Сейчас все вызовы между доменами — локальные (монолит). При выделении:

| Связь | Сейчас | При разделении |
|---|---|---|
| `cases` → владелец (`owner_id`) | FK + relationship | identity API или реплика user-id |
| `analysis` → факты дела | FK `signal_facts.fact_id` | documents API (read) |
| `reporting` → всё дело | ORM-чтение | fan-out вызовыов или read-модель |
| audit-лента | `case_events` | events через outbox → брокер |

**Domain events / outbox** — следующий шаг: таблица `outbox_events`
(`id, aggregate_id, type, payload, created_at`) в домене-источнике + фоновый
relay. Публикует события вида `case.created`, `document.ready`, `analysis.completed`,
`decision.recorded`. Потребители (reporting, уведомления) подписываются позже.
Брокер (Kafka/NATS) на прототипе не поднимаем — outbox даёт тот же контракт,
но без инфраструктуры.

## 6. Порядок выделения (migration path)

1. **Phase 0 — сейчас**: модульный монолит, общая БД, домены изолированы кодом.
2. **Phase 1**: выделить `identity` (самая чистая граница: users+sessions,
   нет входящих FK) — первый сервис с собственной БД и internal auth.
3. **Phase 2**: `documents` (pipeline изолирован, вход — файлы, выход — факты).
4. **Phase 3**: `analysis` (правила — чистая функция от снапшота фактов,
   идеальный кандидат на отдельный worker).
5. **Phase 4**: `cases` + `reporting` — orchestrator-слой последним.

Критерий готовности домена к выделению: его `services.py` не импортирует ORM-
модели чужих доменов (только id/DTO), а запись в чужие таблицы отсутствует.

## 7. Что осознанно НЕ делаем на этом этапе

- Отдельные БД на сервис — преждевременно: схема ещё меняется, общая БД упрощает
  миграции и e2e. Переход — database-per-service по мере выделения (Phase 1+).
- Kubernetes, service mesh, API-gateway, брокер сообщений — избыточно для
  прототипа; docker-compose с двумя сервисами (frontend+backend) остаётся.
- gRPC — REST/OpenAPI уже покрывает контракт клиента; gRPC добавим только если
  появится сервис-сервис трафик, который его оправдает.

## 8. Чек-лист для нового эндпоинта

1. Определить домен-владелец ресурса (см. §2) — эндпоинт идёт в его `api.py`.
2. Схемы запроса/ответа — в `schemas.py` домена, не в `core`.
3. Логика — в `services.py` домена; сессия БД — через `core.deps.get_db`.
4. Если нужен чужой ресурс — через его `services.py` (позже — через API),
   не через прямой запрос к чужим таблицам без необходимости.
5. Модель — в `models.py` домена-владельца; FK на чужие таблицы — только через
   `TYPE_CHECKING`-relationship, зафиксированный как шов выделения.
