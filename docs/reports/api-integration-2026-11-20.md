# API-интеграция финансового профиля · 20.11.2026

## Результат и область

Оставлен один финансовый профиль с API на `/` для всех ролей; `/prototype` — совместимая ссылка. `FinancialProfile` работает с расширенным `app/domains/profile/`, без отдельного in-memory хранилища. Старый frontend `src/app/` удалён; прежние серверные `cases`, `documents`, `analysis`, `reporting` и их данные сохранены без отдельного интерфейса.

Согласованные исходники находятся только в `fullstack/`. Старые экспорты/исходники Дарьи и удалённый сервер не заменены; GitHub не изменён. Локальный `resonance-fullstack.zip` пересобирается из текущего дерева, а не из соседней старой копии. [Финальная очистка UI](single-interface-2026-11-20.md) не меняет backend, миграции и этот профильный контракт.

## Модель и транспорт

- Авторизация: same-origin `/api/auth/*`, серверная cookie-сессия HttpOnly/SameSite. Профильные запросы передают `X-Profile-Account` с текущим username; несовпадение аккаунта — 409, а не запись в другой профиль.
- Контракт ответа профиля/карточки: `contract_version: "questionnaire-v1"`. Старый сервер отклоняется клиентом с понятным сообщением; одного изменения прокси недостаточно.
- `profiles.questionnaire` хранит типизированный агрегат: кандидат, периоды, родство, получатели, ответы/записи десяти категорий, деятельность, приложения, согласие, фото и сохранённые legacy-реквизиты.
- Строки и исходные даты/суммы в агрегате не нормализуются на стороне клиента. Старые SQL-поля — совместимая ограниченная проекция; дополнительные сведения, точные строки и логические ID сохраняются в агрегате.
- `revision` растёт при профильных мутациях. Владелец обязан передать текущую ревизию для PUT, загрузки, удаления и отправки. Устаревшая ревизия — 409; молчаливой перезаписи нет.
- `private_reply` хранится отдельно от переданной версии; при повторной отправке переходит в неизменный слепок и сообщение. Сохранять черновик и отправлять его — разные операции.
- Оригиналы хранятся в `UPLOAD_DIR/profiles/<profile_id>/` с отдельным UUID-префиксом, неизменным ID и SHA-256. Blob-URL в БД не сохраняются. Удаление документа мягкое и очищает только ссылки черновика.

Клиент читает согласованные ревизии нескольких ответов перед гидратацией, сериализует сохранения/мутации и ждёт подтверждения перед выходом. Ошибка обновления экрана после успешной мутации не сообщается как отсутствие серверного сохранения. Перед перезагрузкой с несохранёнными изменениями предлагается локальная JSON-копия.

## Основные операции

| Операция | Контракт / ограничение |
|---|---|
| `GET /api/profile` | собственный агрегат; новый профиль создаётся пустым |
| `PUT /api/profile` | полный `questionnaire`, текущая `revision`, опциональный `private_reply`; только draft/clarification; ответ — подтверждённый DraftOut |
| `GET /api/profile/completeness` | семь групп и вехи 10/30/50/70/90, missing, can_submit |
| `POST /api/profile/documents` | multipart: file, kind, section, revision; ответ DocumentOut с новым ID, profile_revision и URL |
| `DELETE /api/profile/documents/{id}?revision=n` | мягкое удаление, 204; существующие версии/оригиналы остаются |
| `POST /api/profile/submit` | JSON: confirmed=true, revision; сервер требует комплектность/согласие; 201 VersionDetailOut с profile_revision |
| `GET /api/profile/versions[/{number}]` | неизменные версии; URL оригинала связан с номером версии |
| `GET /api/profile/review-state` | свои оценки, итог и доступные файлы результата |
| `GET /api/profile/messages`, `/signals`, `/audit` | состояние своего профиля; личная история доступна только владельцу |
| `POST /api/profile/events` | ограниченный журнал просмотра/печати/самопроверки/открытия/запроса выхода; scope определяет сервер |
| `GET /api/reviewer/queue` | только назначенные представленные материалы, счётчики текущей версии |
| `GET /api/reviewer/profiles/{id}?version=n` | слепок версии, сигналы/решения, оценки, сообщения, итог; не черновик |
| `POST /api/reviewer/profiles/{id}/documents` | файл результата, обязательный version; не файл приватного черновика |
| `POST …/documents/{doc_id}/assessment` | version, status usable/details/unreadable, comment ≥5; request_clarification — явное действие |
| `POST /api/reviewer/signals/{id}/decision` | version, status reviewed/clarification/dismissed/included, comment ≥5; append-only |
| `POST /api/reviewer/profiles/{id}/decision` | action accept/clarification/complete/remove, version, comment, basis, document_id, checks |
| `GET …/versions`, `/diff`, `/audit`, `/export` | только доступный опубликованный контур; private-события не выдаются |
| `GET /api/reference/contacts`, `/rules` | вымышленные контакты и правила по введённым сведениям, не внешний реестр |

Полная машиночитаемая схема формируется backend на `/openapi.json` (48 путей приложения). В PUT нужно передавать **весь** полученный агрегат, а не только изменённую строку. Не отправляйте старое тело без revision и не смешивайте contract_version клиента с версией слепка.

## Приватность и доступ к оригиналам

Каждая reviewer-операция требует роли reviewer/specialist **и** назначения. `specialist` не является обходом. Файловый маршрут проверяет ID профиля, назначение и принадлежность файла выбранной представленной версии. Файл результата до фиксации итога видит загрузивший его назначенный проверяющий; после решения — владелец и уполномоченный контур.

Личный черновик, скрытые записи, новые личные загрузки и пояснение не подмешиваются в версию. Новые сохранённые данные не меняют старые слепки; доступ к старому одноимённому файлу не заменяется URL новой загрузки. Скрытые условные поля не возвращаются через legacy-метаданные в слепок/печать.

API устанавливает no-store. Оболочка приложения запрещена в iframe; только оригиналы файлов и учебные приложения имеют same-origin-разрешение для просмотра. Nginx/Vite-preview не должны дополнять файловые ответы оболочечным DENY/CSP.

## Человеческое рассмотрение

Сигналы `РО-01`, `ДУ-01`, `ДЕ-01` строятся только по анкетным значениям. Они не являются обвинением или выводом OCR. Возможный дубль не вычитается, основание компенсации не исправляется автоматически; пересечение периодов требует человеческой правовой оценки.

Оценка файла и решение сигнала сохраняются с комментарием и версией. Старая версия только читается. Итоговое complete/remove требует:

1. Три явных подтверждения специалиста.
2. Комментарий не короче 10 символов и реквизиты основания не короче 5.
3. Доступный файл результата, загруженный для текущей версии.
4. Терминальное решение каждого сигнала с последним соответствующим комментарием.
5. Комментированную оценку usable каждого не-фото приложения текущей версии и доступные оригиналы.
6. Отсутствие незавершённого статуса clarification; после финала новые мутации запрещены.

Для согласия проверяется наличие отдельного доступного файла нужного вида, не подлинность подписи. При уточнении новая отправка требует заполнения и пояснения ≥10 символов. Денежные записи резервиста и членов семьи считаются отдельно; натуральные/жилищные/неденежные меры не прибавляются.

## Демо без перезаписи

Запуск backend добавляет только отсутствующие учебные аккаунты/контакты; существующие имена, роли и пароли не меняются. Новая анкета не заполняется именем аккаунта.

`POST /api/profile/demo` допустим только в нетронутом draft с revision=0, без документов/версий/прежних данных. Он добавляет синтетические сведения по явному запросу, **не отправляет** их. Сервер использует 12 существующих PDF и манифест из `demo_data`, без генерации официальных форм.

`POST /api/reviewer/demo` создаёт или открывает отдельный готовый комплект с техническим владельцем и назначением текущему проверяющему. Он не изменяет `reservist`, не раскрывает его черновик и не создаётся автоматически при старте.
