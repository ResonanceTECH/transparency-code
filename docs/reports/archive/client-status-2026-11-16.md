## 1. Общая архитектура

Одна точка входа (`index.html` → `src/main.tsx`) монтирует **два независимых интерфейса** по маршруту:

| Маршрут | Компонент | Назначение | Бэкенд |
|---|---|---|---|
| `/prototype` | `FinancialProfile` (`src/financial-profile.tsx` + `.css`, ~500 + ~750 строк) | Актуальный самостоятельный макет «финансовый профиль резервиста» | Не нужен |
| `/` (все прочие пути) | `App` (`src/main.tsx` + `src/styles.css`) | Интеграционный интерфейс «проверка сведений» с реальными API-запросами | Требуется (`/api` → `127.0.0.1:8000`) |

Дополнительно сохранён исторический макет `src/prototype.tsx` + `prototype.css` (предыдущая итерация, не подключён к роутингу — оставлен для справки).

Управление состоянием везде — локальный `useState` React; роутинг — не через react-router, а через переключение `screen`/`view` в state. В `/prototype` весь стейт живёт только в памяти открытой страницы (перезагрузка = сброс демо).

## 2. Макет `/prototype` — финансовый профиль резервиста

### 2.1. Роли

Реализованы две демонстрационные роли с переключением в верхней панели (`fp-role-switch`):

- **Резервист** — вымышленный «Ковалёв Алексей Сергеевич», профиль `РВ-2026-0147`. 8 разделов: Главная, Профиль и служба, Родство и получатели, Выплаты и меры, Деятельность, Документы, Самопроверка, Уточнения + Инструкция.
- **Проверяющий** — уполномоченный кадровый специалист «Анна Иванова». 6 разделов: Поступило на проверку, Карточка резервиста, Сопоставление, Запросы уточнений, Результат рассмотрения, Версии и журнал + Порядок рассмотрения.

**Модель доступа (ключевая механика макета):** до отправки сведений у проверяющего заблокированы все разделы, кроме очереди — отображается заглушка «Материал ещё не представлен». Проверяющий видит только **зафиксированный снапшот** (`PresentedSnapshot`), а не живой черновик: редактирование контактов/программы резервистом после отправки не меняет представленную версию до повторной отправки. Это покрыто тестами.

### 2.2. Жизненный цикл профиля (фазы)

```
draft → submitted → clarification → resubmitted → completed | removed
```

- `draft` — личный черновик, прогресс 70% (неполный) / 90% (все обязательные блоки).
- `submitted` — после самопроверки 6/6 и чекбокса согласия создаётся снапшот версии 1, доступ назначается кадровому специалисту.
- `clarification` — специалист запросил уточнение (комментарий ≥5 символов обязателен); у резервиста появляется запрос и форма ответа.
- `resubmitted` — резервист подготовил версию 2 (пояснение ≥10 символов + 3 чекбокса исправлений) и повторно отправил; уточнённые данные (исключён дубль, уточнено основание, новые контакты) видны проверяющему.
- `completed` / `removed` — итоговый статус фиксирует специалист: обязательны 3 чекбокса проверки, комментарий ≥10, реквизиты основания и подтверждающий документ. Результат виден резервисту на главной и в разделе результата.

### 2.3. Экраны резервиста

- **Главная (`home`)**: карточка личности с кольцом прогресса (`role="progressbar"`, 70/90%), список разделов с бейджами готовности, последние действия из журнала, приватность-уведомление. После завершения рассмотрения — результат, основание и список версий.
- **Профиль и служба (`profile`)**: редактируемые поля — год рождения, телефон, email, регион, поток и год «Время героев», региональная программа и её год, предполагаемый орган назначения (селект из 3 опций), статус работы (селект); статичные учебные поля (ФИО, место работы, организатор, реквизиты диплома и акта); периоды службы (военная 01.06.2023–31.08.2025 + иное место работы); загрузка фото (демо).
- **Родство и получатели (`kinship`)**: вопрос о родстве с участником СВО — при «Да» открываются ФИО, степень родства (селект из 4), статус (селект из 4); при «Нет» поля скрываются. Отдельный блок «выплата члену семьи за резервиста» (ФИО, связь, год рождения, обязательный документ). Цепочка «получатель → связь → основание» и карточка о минимуме данных родственника.
- **Выплаты и меры (`payments`)**: сводка «10 из 10 ответов», таблица **10 категорий** с ответами Да/Нет/Планируется, статусами готовности и переходами в детальные формы. Подсветка недостающих обязательных данных (файл региональной поддержки, год жилищной меры).
- **Категория (`category`)**: универсальная форма для категорий без отдельного экрана — денежное довольствие и надбавки (период, плательщик, получатель, приказ + опциональное основание), выплаты членам семьи, материальная помощь (денежная/натуральная форма — натуральная не идёт в доход), пенсии (только ответ, документ **не** запрашивается), неденежные меры.
- **Единовременная выплата (`payment`)**: событие, вид события, дата, категория получателя (сам резервист / член семьи / резервист за родственника), сумма, плательщик, нормативное основание с редакцией, **период основания отдельно от даты фактического перечисления**, идентификатор назначения «Н-42» (помогает сопоставлять записи и искать дубли).
- **Поддержка (`support`)**: три уровня — федеральная (Нет), региональная (Да), муниципальная (Нет); форма полученной меры (уровень, орган, наименование, код, дата, получатель, сумма); **обязательная загрузка документа-основания** через `UploadBox` (accept `.pdf,.doc,.docx`) — без файла отправка версии блокируется.
- **Страховые выплаты (`insurance`)**: раздельно личные выплаты (Нет) и выплаты за родственника (Да); визуальная цепочка получатель→родственник→решение № К-24; селект основания «за личное участие / в связи с родственником» — в версии 2 исправляется.
- **Жилищные меры (`housing`)**: три состояния Да/Планируется/Нет. «Планируется» требует год по паттерну `^20\d{2}$` с инлайн-ошибкой, статус и документ-основание; «Нет» закрывает поля; «Да» открывает вид меры (субсидия/компенсация/жильё/кредит отдельно).
- **Деятельность (`activities`)**: ответ Да/Нет; при «Да» — организация, вид деятельности (5 опций), вид оформления (5 опций, включая ГПД и безвозмездную), период, реквизиты договора № П-18/25, документ.
- **Документы (`documents`)**: реестр из 9 учебных документов + загруженное основание поддержки, привязка файлов к разделам, просмотр в модалке, индикатор недостающего основания, карточка источников (ручная загрузка доступна, ведомственные источники — нет).
- **Самопроверка (`selfcheck`)**: 6 контрольных блоков комплектности с навигацией к незаполненному; **повторный пересчёт без перезагрузки** (кнопка `RotateCw`), сводка (10/10 ответов, записей, документов, получателей), чекбокс согласия и кнопка «Отправить на проверку» (дизейбл до `ready && consent`); после отправки — состояние «версия передана».
- **Уточнения (`messages`)**: вопрос специалиста с бейджами тем, форма пояснения резервиста, 3 чекбокса исправлений, кнопка «Подготовить версию 2»; у проверяющего — статус ожидания ответа.
- **Инструкция (`instructions`)**: этапы 10/30/50/70/90%, правила документов и исключений, раздельный учёт, приватность черновика, ограничения макета.

### 2.4. Экраны проверяющего

- **Очередь (`queue`)**: 4 статистические карточки, поиск по ФИО/номеру, вкладки-фильтры (Все/Поступило/На уточнении/Завершено), таблица назначенных материалов (динамическая строка Ковалёва + 2 учебных соседа).
- **Карточка резервиста (`case`)**: шапка из представленной версии, счётчики документов и рассмотренных вопросов, кнопка «Принять к рассмотрению» → «Сопоставить»; сведения комплектности, финансовая сводка (2 580 000 ₽ по v1 / 2 430 000 ₽ по v2 — дубль исключён; 120 000 ₽ члену семьи отдельно), неденежные/планируемые меры отдельными строками; список из 3 вопросов; замечание о поздней дате перечисления («прямое противоречие дат не сформировано»).
- **Сопоставление (`signals`)**: 3 сигнала по схеме «представленные сведения ↔ документ-основание» с цитатой фрагмента и рекомендуемым действием:
  - `РО-01` — выплата за родственника записана как личная;
  - `ДУ-01` — возможный дубль по назначению Н-42;
  - `ДЕ-01` — договор преподавания пересекается со службой.
  Действия по каждому: **запросить уточнение / отметить рассмотренным / исключить с обоснованием** — все требуют комментарий ≥5 символов; статусы отображаются в списке и карточке.
- **Запросы уточнений (`messages`)**: тот же экран сообщений в роли проверяющего — история запроса, ожидание ответа, ответ после повторной отправки.
- **Результат (`result`)**: выгрузка учебного JSON (`resonance-demo-result.json` через Blob), форма итогового статуса с валидацией (3 чекбокса + комментарий + основание + документ), выбор «Рассмотрение завершено / Снят с рассмотрения»; после фиксации — баннер результата, основание, документ, рассмотренные вопросы.
- **Версии и журнал (`history`)**: карточки версий 1 и 2, таблица аудита (дата/пользователь/действие/доступ) — проверяющему показываются только события со scope `submitted`, личные действия черновика скрыты.

### 2.5. Аудит и уведомления

`AuditEvent[]` с полями `action/actor/scope('private'|'submitted')/time`; логируются просмотры экранов, загрузки, самопроверки, представления версий, решения по сигналам, выгрузка. Тосты (`fp-toast`) с автоскрытием 3.2 c. Модалка просмотра учебного документа с пояснением «не реальный документ, не OCR».

### 2.6. UI-слой и доступность

Переиспользуемые компоненты: `Badge` (5 тонов), `Panel`/`PanelTitle`, `Notice`, `Field` (текст/select, required/optional, ошибка, подсказка), `Choice` (Да/Нет[/Планируется], `aria-pressed`), `FileRow`, `UploadBox` (реальный `<input type="file">`), `Ring` (прогресс на CSS-переменной), `PersonHeader`. Иконки — lucide-react. Aria-атрибуты на интерактивных элементах, `role="navigation"`, `role="status"`, `aria-modal`. Адаптив: мобильное меню-оверлей, проверка отсутствия горизонтального скролла на 390×844 в тестах.

## 3. Интеграционный интерфейс `/` (с реальным API)

Клиент для отдельного бэкенда (исходников в репо нет). Функциональность:

- **Аутентификация**: `GET /auth/me` при старте (401 → экран входа), `POST /auth/login` (демо-аккаунт `demo / resonance-demo-2026`), `POST /auth/logout`.
- **Дашборд (`overview`)**: 4 статистики по делам, три демо-сценария — «Trade-in автомобиля», «Покупка квартиры», «Чистый комплект» (`POST /cases` + `POST /cases/:id/demo?kind=…&clean=…`).
- **Реестр (`checks`)**: поиск по номеру/ФИО/подразделению, фильтр статусов, таблица дел, счётчики сигналов, индикатор «нужен повторный анализ» (`stale`).
- **Создание дела (`new`)**: форма — основание (candidate/expense_review), имя, подразделение, отчётный год → `POST /cases` → переход к документам.
- **Карточка дела (`case`)**: шапка лица, инфо-грид, табы, первые 8 фактов, таймлайн событий.
- **Документы (`documents`)**: список документов дела со статусом извлечения, скачивание, drag&drop-загрузка JSON/XLSX/PDF/DOCX до 5 МБ (`FormData`, `POST /cases/:id/documents`), подтверждение всех фактов, **редактирование факта в модалке** (`PATCH /facts/:id` — значение, дата, единица, флаг «сверено»).
- **Анализ (`analysis`)**: `POST /cases/:id/analysis-runs` с выбранными правилами; переключатель запусков (последний/архивные), карточки сигналов с правилом, версией правил, числом оснований; пустое состояние без сигналов.
- **Сигнал (`evidence`)**: сопоставление значений-оснований с цитатами, история решений, форма решения специалиста — статусы «Запросить доп. сведения / Расхождение объяснено / Дальнейшее рассмотрение» с обязательным комментарием.
- **Правила (`rules`)**: переключатели детерминированных правил для следующего запуска; старые запуски не переписываются.
- **Итог (`report`)**: рабочий документ — метаданные, хэш снимка `input_hash`, таблица сигналов, решения специалиста; выгрузка JSON и печать/PDF.
- **Прочее**: модалка «О системе», устаревание снимка (`stale` блокирует решения), обработка `ApiError` с русскими сообщениями, 401 → сброс сессии.

Типы API в `src/types.ts`: `CaseSummary`, `CaseDetail`, `Fact`, `Signal`, `Run`, `Rule`, `Decision`, `View`. Клиент `src/api.ts` — тонкая обёртка fetch с `credentials: 'same-origin'`, JSON-заголовками и `ApiError`.

## 4. Тестирование

**`tests/profile.spec.ts`** — 7 браузерных тестов макета (Playwright поднимает Vite сам, порт 4173, `PROTOTYPE_URL`/`PROTOTYPE_PORT` для переопределения):

1. Прогресс-кольцо, этапы инструкции, приватность черновика, блокировка отправки до обязательных полей;
2. «Нет» скрывает условные поля; пенсии без документа; жильё «Планируется»;
3. У каждого сигнала своё основание; поздняя дата перечисления ≠ нарушение;
4. Черновик ответа и контакты приватны до повторной отправки; завершение требует основания человека;
5. Правки контактов/программы сохраняются локально, но не меняют представленный снапшот;
6. Повторная самопроверка пересчитывает без перезагрузки и потери вложений; аудит не содержит личных действий;
7. Мобильная вёрстка 390×844 без переполнения.

**`tests/flow.spec.ts`** — 4 интеграционных теста с полным бэкендом на `127.0.0.1:8080`: полный цикл trade-in (импорт → подтверждение → анализ → решение → правка факта → повторный анализ → отчёт), мобильная оболочка, загрузка JSON и скачивание итога, Swagger-документация со строгим CSP и без внешних запросов.

## 5. Сборка и инфраструктура

- `vite.config.ts`: React-плагин, прокси `/api` и `/openapi.json` → `127.0.0.1:8000`.
- `Dockerfile`: двухстадийная сборка `node:22.15.0-alpine` → `nginx:1.28.0-alpine`, `npm ci`, `npm run build`.
- `nginx.conf`: жёсткий CSP (`script-src 'self'` и пр.), security-заголовки, `client_max_body_size 6m`, прокси `/api/` → `backend:8000`, статика `/docs/`, SPA-fallback на `index.html`.
- `public/docs/` + `tools/copy-docs.mjs`: офлайн Swagger UI (копируется из `swagger-ui-dist` перед `dev`/`build`, чтобы работать под CSP без внешних CDN).
- `tools/capture-financial-profile.mjs`: генерация 23 PNG-скриншотов макета; `capture-prototype.mjs` — исторический скрипт.
- `package.json`: scripts `dev`, `dev:prototype` (4173), `build` (`tsc -b && vite build`), `preview` (4174), `typecheck`, `test:prototype`, `test:e2e`, `screenshots:prototype`; engines Node ≥22/npm ≥10.

## 6. Покрытие CRUD

| **Create** | записи/ответы категорий, вложения, комментарии и решения сигналов, запрос уточнения, ответ резервиста, снапшоты версий 1/2, события аудита | дела, демо-комплекты, документы (upload), запуски анализа, решения по сигналам, сессия (login) |

| **Delete** | не реализовано (исключение вопроса — статус, не удаление) | не реализовано в UI |

## 7. Ограничения и пробелы

- Весь стейт макета — в памяти страницы; нет персистентности, URL-роутинга и deep-links.
- Бэкенд и БД отсутствуют в репозитории: интеграционный режим и `flow.spec.ts` требуют внешний сервис.
- Демо-данные захардкожены константами; нет реального CRUD по множественным резервистам (в очереди 2 статических соседа).
- **В репозитории отсутствуют `.gitignore`, `.nvmrc` и `.github/workflows/ci.yml`**, хотя README на них ссылается (вероятно, потерялись при загрузке через веб-интерфейс GitHub). В корне лежат `package-lock.json` и пр., но без `.gitignore` риск случайно закоммитить `node_modules`/`dist`.
- `src/prototype.tsx` — устаревшая итерация, не подключена; поддерживается только для истории.
- Нет i18n-инфраструктуры (только русский), нет темы/токенов дизайна вне `financial-profile.css`.
- Предпросмотр «документа» — текстовая модалка, не реальный просмотр PDF.
