`backend/tests/test_persistent_profile_contract.py` (7/7) проверяет:

3. Демо-заполнение явно и допустимо только один раз для нетронутого профиля; готовый сценарий не перезаписывает существующие сведения.
4. Демо-комплект проверяющего — отдельный материал с версией и назначением; личный черновик `reservist` остаётся пустым.
5. Два одинаковых файла получают разные ID; мягкое удаление убирает ссылку из черновика, но сохраняет второй оригинал.
6. Итоговое решение с неверной версией — 409; `complete` без файла результата текущей версии — 422; материал остаётся доступным, автоматического отказа нет.

## Почему падают старые тесты

Все 18 падений pytest приходятся на исторические контракты:

- `tests/test_auth.py` ожидает, что сид при старте **перезаписывает** имя существующего `reservist`. Сейчас имена/роли/пароли сохраняются — это было отдельным требованием.
- `tests/test_profile.py`: PUT без `revision` (сейчас 422), отправка без `confirmed`/согласия (422), старые правила сигналов `period-order`/`housing-kind-required` вместо `РО-01`/`ДУ-01`/`ДЕ-01`, ожидание дедупликации файлов по SHA-256 (сейчас каждый файл имеет отдельный ID), а также старые имена/структура полей ответа.

Playwright-падения объясняются тем, что `tests/prototype.helpers.ts` подменяет только авторизацию и рассчитывает на мгновенно заполненный сценарий Ковалёва в памяти. Текущая модель загружает профиль с сервера: на чистом профиле нет категорий, счётчиков и уведомлений; часть локаторов относится к удалённому `src/app/` (`flow.spec.ts`). Визуальные эталоны сняты до API-интеграции и до очистки интерфейса; e2e-конфигурация требует Docker/стек на порту 8080.

Эти тесты **сохранены без изменения** как исторические материалы. Их прежние успешные результаты в архивных отчётах не подтверждают текущую интеграцию; перед использованием как критерия приёмки нужна отдельная актуализация под API.

## Ограничения прогона

Прогон не является полным подтверждением многопользовательского цикла: Playwright не проверял реальную публикацию, назначения и человеческие решения через API (мокировалась только авторизация), а e2e-стек не поднимался. Backend-тесты используют in-memory SQLite, а не PostgreSQL. Безопасность, production-развёртывание и совместимость с реальными ПДн не проверялись.
