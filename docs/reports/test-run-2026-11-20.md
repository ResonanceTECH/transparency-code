## Что прошло в новом контрактном наборе

`backend/tests/test_persistent_profile_contract.py` (7/7) проверяет:

1. Новый профиль пустой и отдает `contract_version: "questionnaire-v1"`, `revision: 0`, `progress: 0`, `can_load_demo: true`; отправить его нельзя.
2. PUT без `revision` отвергается; устаревшая ревизия даёт 409; свежая — сохраняет `private_reply`.
3. Демо-заполнение явно и допустимо только один раз для нетронутого профиля; готовый сценарий не перезаписывает существующие сведения.
4. Демо-комплект проверяющего — отдельный материал с версией и назначением; личный черновик `reservist` остаётся пустым.
5. Два одинаковых файла получают разные ID; мягкое удаление убирает ссылку из черновика, но сохраняет второй оригинал.
6. Итоговое решение с неверной версией — 409; `complete` без файла результата текущей версии — 422; материал остаётся доступным, автоматического отказа нет.

## Что исправлено в backend-тестах

- `test_auth.py`: вместо ожидания перезаписи имени проверяется, что сид создаёт только отсутствующие аккаунты, а существующие имя/роль/пароль/ID сохраняются; добавлен тест восстановления только удалённого аккаунта.
- `test_profile.py`: PUT/загрузка/удаление/submit передают актуальную `revision`; submit — `confirmed: true`; для публикации через `/profile/demo` добавляются обязательное согласие, документ поддержки и год жилья; ожидаются правила `РО-01/ДУ-01/ДЕ-01`; проверяются отдельные ID одинаковых файлов, мягкое удаление, привязка решений к версии и полное человеческое закрытие (сигналы, оценки, файл результата, три подтверждения).
- Добавлен `test_persistent_profile_contract.py` с 7 тестами текущего контракта; архивные копии старых тестов лежат в `tests/archive/` и не собираются.

Playwright-падения объясняются тем, что `tests/prototype.helpers.ts` подменяет только авторизацию и рассчитывает на мгновенно заполненный сценарий Ковалёва в памяти. Текущая модель загружает профиль с сервера: на чистом профиле нет категорий, счётчиков и уведомлений; часть локаторов относится к удалённому `src/app/` (`flow.spec.ts`). Визуальные эталоны сняты до API-интеграции и до очистки интерфейса; e2e-конфигурация требует Docker/стек на порту 8080. Эти UI-тесты пока **не адаптированы**; их повторный прогон остаётся отдельной задачей.

## Ограничения прогона

Прогон не является полным подтверждением многопользовательского цикла: Playwright не проверял реальную публикацию, назначения и человеческие решения через API (мокировалась только авторизация), а e2e-стек не поднимался. Backend-тесты используют in-memory SQLite, а не PostgreSQL. Безопасность, production-развёртывание и совместимость с реальными ПДн не проверялись.
